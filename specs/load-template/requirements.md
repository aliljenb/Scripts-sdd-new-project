# Requirements: load-template

- [x] Draft

## Introduction
A Bash script for macOS that scaffolds a new spec-driven development (SDD) project for Python. The workflow is Kiro-style (requirements → design → tasks) but is driven by the Claude CLI instead of Kiro: the generated project includes a `.claude/skills/` directory with slash commands that implement the SDD lifecycle. The script interactively prompts for a project name and Python module name, then constructs the project by cloning a fixed GitHub template repository into the Project_Root, renaming the template's placeholder Python package to the user-provided module name, and re-initializing the directory as a fresh local git repository with its own initial commit — independent of the template repository's own git history.

## Glossary

- **Script**: The Bash shell script, named `new-sdd-project.sh`, that performs the scaffolding operation
- **Project_Root**: The top-level directory created by the Script, named after the user-provided project name
- **Template_Repository**: The fixed GitHub repository the Script clones to construct the Project_Root, located at `https://github.com/aliljenb/Scripts-sdd-template.git`. Not user-configurable.
- **Placeholder_Package**: The Python package directory at the fixed path `src/python_module/` in the Template_Repository — the single package directory under `src/` — which the Script renames to the user-provided Python_Package name after cloning
- **Python_Package**: A directory within `src/`, originally cloned as the Placeholder_Package and renamed to the user-provided module name, containing an `__init__.py` file
- **Test_Package**: A `tests/` directory at the Project_Root level, sourced from the Template_Repository, containing an `__init__.py` file and a placeholder `test_<Python_Package>.py` file that imports pytest and is decorated with the `@pytest.mark.smoke` marker
- **Project_Manifest**: A `pyproject.toml` file at the Project_Root level, generated by the Script (not sourced from the Template_Repository, since it embeds the user-provided project name), that declares the project name, declares `pytest` as a development dependency, and registers the `smoke` pytest marker
- **Readme_File**: A `README.md` file at the Project_Root level, generated by the Script (not sourced from the Template_Repository), containing a top-level heading with the project name and a short generic placeholder description line
- **Claude_Skills**: Markdown files placed in `.claude/skills/`, sourced from the Template_Repository, that define Claude CLI slash commands for the SDD lifecycle (`spec-requirements`, `spec-design`, `spec-tasks`, `implement-task`, `review`)
- **Spec_Templates**: Markdown template files (`template.md`) placed in the `<Claude_Skills>/<Skill>` directory, sourced from the Template_Repository, following Kiro-style conventions
- **Suggested_Module_Name**: A valid Python identifier computed by the Script from the user-provided project name, offered as the pre-filled default value at the Python module name prompt (see Story 1)


## User stories

### Story 1: Project configuration prompts

> As a **developer**, I want **the script to prompt me for project configuration**, so that **the generated project matches my naming preferences**.

**Acceptance criteria:**

- [ ] WHEN the Script is executed, THE Script SHALL prompt the user for a project name via standard input
- [ ] WHEN the project name has been prompted for and validated, THE Script SHALL prompt the user for a Python module name via standard input, displaying the Suggested_Module_Name as the pre-filled default in that prompt
- [ ] WHEN the user provides a project name, THE Script SHALL use that value as the Project_Root directory name
- [ ] WHEN the user submits a non-empty value at the Python module name prompt, THE Script SHALL use that typed value as the Python_Package directory name within `src/`, in place of the Suggested_Module_Name
- [ ] WHEN the user submits an empty value at the Python module name prompt, THE Script SHALL use the Suggested_Module_Name as the Python_Package directory name

### Story 2: Input validation

> As a **developer**, I want **input validation**, so that **the script does not create malformed or conflicting project structures**.

**Acceptance criteria:**

- [ ] IF the user provides an empty project name, THEN THE Script SHALL display an error message and exit with a non-zero status code
- [ ] IF the user submits empty input (presses Enter without typing a value) at the Python module name prompt, THEN THE Script SHALL treat this as acceptance of the Suggested_Module_Name (Story 1) rather than as an error, since a valid non-empty suggestion is always available by that point in the prompt flow
- [ ] IF the user provides a module name that is not a valid Python identifier (does not match `^[a-zA-Z_][a-zA-Z0-9_]*$`), THEN THE Script SHALL display an error message and exit with a non-zero status code
- [ ] IF a directory matching the Project_Root name already exists in the current working directory, THEN THE Script SHALL display an error message and exit with a non-zero status code
- [ ] THE Script SHALL perform all validation before creating any files or directories

### Story 3: Template-based project scaffolding

> As a **developer**, I want **the script to build the new project from a GitHub template**, so that **I get a project structure that stays consistent with the shared SDD template instead of being regenerated ad hoc by the script**.

**Acceptance criteria:**

- [ ] WHEN project name and module name validation (Story 2) has passed, THE Script SHALL clone the Template_Repository into a directory named after the Project_Root
- [ ] AFTER cloning the Template_Repository, THE Script SHALL rename the Placeholder_Package directory (`src/python_module/`) to the user-provided (or suggested) Python_Package name
- [ ] AFTER renaming the Placeholder_Package, THE Script SHALL generate the Project_Manifest (`pyproject.toml`) at the Project_Root, populated with the user-provided project name, overwriting any `pyproject.toml` present in the Template_Repository
- [ ] AFTER generating the Project_Manifest, THE Script SHALL generate the Readme_File (`README.md`) at the Project_Root, containing a top-level heading with the user-provided project name and a short generic placeholder description line, overwriting any `README.md` present in the Template_Repository
- [ ] AFTER generating the Readme_File, THE Script SHALL remove the cloned `.git` directory so no history or remote from the Template_Repository is retained
- [ ] AFTER removing the cloned `.git` directory, THE Script SHALL initialize a new local git repository at the Project_Root and create an initial commit containing the generated project structure
- [ ] THE Script SHALL NOT generate `src/`, `tests/`, `.claude/skills/`, or spec template files itself — all such content SHALL originate from the Template_Repository; the Project_Manifest (`pyproject.toml`) and the Readme_File (`README.md`) are the two exceptions and SHALL always be generated by the Script

### Story 4: Template retrieval error handling

> As a **developer**, I want **clear errors when the template can't be fetched**, so that **I'm not left with a partially-created, broken project directory**.

**Acceptance criteria:**

- [ ] IF cloning the Template_Repository fails (e.g. no network access, host unreachable, repository not found), THEN THE Script SHALL display an error message and exit with a non-zero status code
- [ ] IF cloning the Template_Repository fails, THEN THE Script SHALL NOT leave a partially-created Project_Root directory behind
- [ ] IF the `git` command is not available on the system, THEN THE Script SHALL display an error message and exit with a non-zero status code before attempting to clone


## Out of scope

- Making the Template_Repository URL user-configurable (fixed per this spec's decision)
- Supporting multiple/selectable templates
- Preserving or merging the Template_Repository's own git history into the generated project
- The Script's own inline generation of project files via heredocs, except for the Project_Manifest (`pyproject.toml`) and the Readme_File (`README.md`) per Story 3, which the Script still generates directly
